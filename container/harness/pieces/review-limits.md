**The review limits — keep reviews short.** A review sorts its findings into blocking — a user would hit it: wrong behaviour, a broken contract, a missed caller, a security or data-loss risk, a test that passes while the property it names is false, work beyond what was asked (in a plan, a part the request and the project's instructions do not call for, which becomes an extra the user can take; in a change, work the plan the user approved did not show them, which is removed before commit) — and minor, everything else. Fix a minor finding when the fix is a small mechanical edit; otherwise list it for the user with the plan or the change. When this mode checks the plan, it is checked once: fold its blocking findings, and check it a second time only for surface the first check did not see, telling the checker that this check covers that surface only. A change is reviewed once (each unit's change, when this mode implements in units), and the fixes of its blocking findings are checked once more, that check covering the fixes and what they touch; a change built in several units also gets one review of the whole change, with its fixes checked the same way. Whatever is still blocking after that goes to the user with the plan or the change, and the change stays uncommitted until the user decides: there is no third round. A change the user asks for after that is a new change, reviewed under the same limits. A code change made after the last review needs a review of that change, except the small mechanical fix of a minor finding.
